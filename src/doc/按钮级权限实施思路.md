# 按钮级权限实施思路（基于当前项目）

## 1. 目标

在现有“菜单/页面权限”基础上，补齐“按钮级权限”，达到以下效果：

- 不同角色进入同一页面时，只看到自己可操作的按钮。
- 前端做显隐与禁用控制，后端做最终鉴权兜底。
- 权限点可在角色管理页面统一配置，不依赖页面里零散硬编码。

## 2. 当前项目现状（已对齐代码）

- 路由已经有功能编号字段：meta.fnId（可作为菜单权限基础）。
- 当前用户信息里已有 menuList，并在页面中使用 includes 判断（例如 TopBar 中的 tab 显示）。
- 某些页面已出现基于 userInfo.menu.xxx 的按钮显隐，但方式不统一、分散在各页面。
- 角色管理页目前维护 menusList（菜单树勾选），尚未看到按钮权限点的统一结构。
- 接口层已有 403 提示（“您没有操作权限”），说明后端已有权限拒绝反馈链路。

结论：项目已经有“菜单权限”骨架，适合在此基础上扩展到“按钮权限”，不建议推翻重做。

## 3. 建议的权限模型

### 3.1 权限对象分层

建议把权限拆成两层：

- 菜单权限（已有）：控制页面可见、路由可访问。
- 操作权限（新增）：控制按钮/操作行为（新增、编辑、删除、导出、审核等）。

### 3.2 按钮权限点命名规范

建议统一使用“页面域.资源.动作”格式，例如：

- home.level.add
- home.level.edit
- home.level.delete
- home.fixedPost.export
- department.user.resetPwd

规范要求：

- 全项目唯一。
- 能从名字看出“在哪个页面、操作什么、做什么动作”。
- 不使用中文或临时缩写，避免后期维护混乱。

### 3.3 用户权限载荷建议

登录后拉取或在用户信息中返回：

- menuList: number[] （继续沿用）
- buttonList: string[] （新增）

前端内存中转成 Set 后查询，保证判定性能。

## 4. 前端落地方案（推荐）

### 4.1 增加 permission 模块（Vuex）

新增 store/modules/permission.js：

- state
  - menuSet
  - buttonSet
- getters
  - hasMenu(fnId)
  - hasBtn(code)
  - hasAnyBtn(codes)
  - hasAllBtn(codes)
- actions
  - initPermission（由 getUserInfo 后触发）
  - clearPermission（退出登录时清理）

这样页面不再直接依赖 userInfo.menu.xxx，统一走权限网关。

### 4.2 增加全局权限指令

在 plugins/directives.js 中新增：

- v-permission="'home.level.add'"
  - 无权限时直接移除节点（按钮不显示）。
- v-permission-disable="'home.level.add'"
  - 无权限时置灰禁用（按钮显示但不可点击，适合保留结构提示场景）。

备注：常规业务按钮建议优先“移除”，导出、审批等关键操作可按产品要求“禁用”。

### 4.3 路由守卫继续用菜单权限

当前 router.beforeEach 仅做进度条，建议补充：

- 若 to.meta.fnId 存在，校验 hasMenu(fnId)。
- 无权限时跳转到 403 页面或首页，并给出提示。

路由守卫负责“页面级准入”，按钮指令负责“页面内操作准入”，职责清晰。

### 4.4 页面使用方式统一

页面中按钮统一改为：

- 查询类基础按钮：默认可见（按业务决定）。
- 修改类/破坏性操作按钮：全部挂 v-permission。
- 行内操作（编辑/删除/重置密码）按权限点逐一挂载。

示例映射建议（可直接执行）：

- 等级管理
  - 新增等级 -> home.level.add
  - 编辑 -> home.level.edit
  - 删除 -> home.level.delete
- 部门管理
  - 新增成员 -> department.user.add
  - 编辑成员 -> department.user.edit
  - 重置密码 -> department.user.resetPwd

## 5. 后端配套改造建议

### 5.1 角色权限结构升级

当前角色是 menusList，建议扩展为：

- menusList: number[]
- buttonsList: string[]

角色管理接口新增/更新时同时保存 buttonsList。

### 5.2 鉴权中间件增加按钮权限校验

对敏感接口（新增/修改/删除/导出）增加操作权限校验，避免前端绕过：

- 前端隐藏按钮只是体验控制，不是安全边界。
- 后端必须以用户身份 + 权限点做最终放行。

### 5.3 权限元数据接口

建议提供“权限字典”接口，返回菜单树 + 按钮点，供角色管理页渲染：

- 菜单节点下挂操作节点（如 add/edit/delete/export）。
- 避免前端写死按钮清单，减少前后端漂移。

## 6. 与现有代码的最小侵入改造顺序

### 阶段 1：基础设施

- 新增 Vuex permission 模块。
- 新增 v-permission 指令。
- 登录后初始化 permission 状态。

### 阶段 2：高风险页面优先

优先改造有破坏性操作的页面：

- 等级管理
- 部门管理
- 游戏渠道
- 固定岗位 / 换绑等含变更动作页面

### 阶段 3：角色管理页支持按钮点配置

- 菜单树扩展操作节点。
- 角色保存时同时提交 buttonsList。

### 阶段 4：全量收敛

- 全仓搜索 el-button、点击事件，逐页补齐权限点。
- 清理旧的 userInfo.menu.xxx 硬编码判断。

## 7. 测试与验收清单

### 7.1 功能验收

- A 角色可见“新增/编辑”，不可见“删除”。
- B 角色仅可查询，不可执行任何写操作。
- 菜单有权限但按钮无权限时，页面可进、操作不可见。

### 7.2 安全验收

- 手工构造请求调用删除接口，后端应返回 403。
- 按钮强行通过浏览器注入显示后，仍无法成功调用敏感接口。

### 7.3 回归验收

- 登录、退出、切换角色后权限立即生效。
- 路由跳转不出现“短暂看到按钮再消失”的闪烁（初始化时机要前置）。

## 8. 常见坑位与规避

- 权限点命名不统一：必须先定规范再铺开。
- 只做前端不做后端：存在真实安全风险。
- 页面内权限判断分散：后期不可维护，必须收敛到统一指令/函数。
- 角色配置数据与前端常量脱节：建议使用后端权限字典驱动。

## 9. 你们项目可直接采用的结论

- 保留现有 menuList + fnId 体系。
- 新增 buttonList + v-permission 体系。
- 菜单权限管“能否进入页面”，按钮权限管“页面内能否操作”。
- 后端接口权限校验作为最终安全边界。

按这个路径实施，改动范围可控、风险低，且能逐步迁移，不会影响当前业务连续性。
