# 部门分管责任人前端更新说明-分管范围收口

## 1. 文档目的

这份文档只说明 2026-03-25 这一轮“分管范围收口”带来的前端影响。

这次不是字段结构调整，而是把部分页面和接口的权限边界补严了。

前端需要重点关注两件事：

- 某些页面现在只能查看当前分管范围内的数据
- 某些接口如果传入了非分管范围的目标用户或目标记录，会直接返回 `401/Unauthorized`

如果前端还沿用旧的“任意传 UserId 查询详情/提交修改”的方式，联调时会出现“后端突然无权限”的现象。

## 2. 本次受影响模块

本次收口影响以下 5 类业务：

- 玩家换绑
- 每日定岗
- 账号关联
- 升级记录
- 经验明细

## 3. 总体行为变化

### 3.1 之前的行为

部分页面虽然列表查询已经按分管部门过滤，但只要前端显式传了某个 `UserId`，或者直接请求了某条详情、编辑、删除接口，仍然可能越过当前分管范围。

### 3.2 现在的行为

后端现在统一按“当前登录人可管理的部门范围 -> 部门下用户范围 -> 目标数据是否属于该范围”进行校验。

如果目标用户或目标数据不在范围内：

- 返回 `401/Unauthorized`
- 不再返回越权数据
- 不再允许越权写入、删除或转移

### 3.3 对前端的直接要求

- 用户选择器不要再放出非当前分管范围内的用户
- 列表页如果支持按 `UserId` 筛选，筛选项必须来自当前可见用户集合
- 详情页、编辑页如果收到 `401`，要提示“无权查看或操作该数据”
- 不要假设“拿到一条记录 ID 就一定能打开详情或保存成功”

## 4. 分模块说明

### 4.1 玩家换绑

接口：

- `GET /api/player/rebind`

当前规则：

- 只能看到当前分管范围内推广账号相关的换绑记录
- 后端会先根据当前分管部门找到用户，再根据这些用户绑定的推广账号过滤换绑数据
- 如果当前分管范围内没有任何账号绑定，接口会返回空列表，不报错

前端影响：

- 玩家换绑页面的数据会比以前更少，这是正常行为
- 页面不要再把“全平台换绑记录”当成默认预期
- 如果页面上有“原推广账号 / 现推广账号”筛选，建议筛选下拉也只显示当前可见账号

联调建议：

- 用一个只分管 A 部门的账号登录，确认只能看到 A 部门相关推广账号的换绑记录
- 再给该账号新增一个分管部门，确认返回结果并集扩大

### 4.2 账号关联

接口：

- `GET /api/userbind`
- `GET /api/userbind/manage`
- `POST /api/userbind`
- `DELETE /api/userbind/{id}`
- `POST /api/userbind/transfer`

当前规则：

- 查询时如果前端传了 `UserId`，该用户必须属于当前分管范围，否则返回 `401`
- 新增账号关联时，目标用户必须属于当前分管范围，否则返回 `401`
- 删除账号关联时，这条关联记录对应的用户必须属于当前分管范围，否则返回 `401`
- 批量转移账号数据时：
  - 目标用户必须在当前分管范围内
  - 被转移的账号也必须至少命中当前分管范围内的一条账号绑定
  - 否则返回 `401`

前端影响：

- 账号关联页的用户筛选框必须限制来源
- “转移到目标用户”这类弹窗，目标用户下拉只能给当前可管理用户
- 从列表点“删除”时，理论上页面上能看到的数据都能删；如果删时报 `401`，说明页面缓存了旧数据或跨页打开了越权记录

前端建议：

- 所有用户下拉统一复用“当前分管范围用户列表”数据源
- `transfer` 失败时，对 `401` 单独提示，不要只显示“操作失败”

建议提示文案：

- `当前账号不在你的分管范围内，无法执行转移`

### 4.3 每日定岗

接口：

- `GET /api/bizconf`
- `GET /api/bizconf/{bizId}`
- `POST /api/bizconf`
- `POST /api/bizconf/bluk`
- `PUT /api/bizconf/{bizId}`
- `DELETE /api/bizconf/{bizId}`

当前规则：

- 列表按当前分管范围过滤
- 如果前端传 `UserId` 查询，则该用户必须属于当前分管范围，否则返回 `401`
- 单条详情、修改、删除时，配置中的 `AUserId`、`BUserId`、`CUserId` 至少要有一个落在当前分管范围内，否则返回 `401`
- 新增和批量新增时，如果选择的用户都不在当前分管范围内，也会返回 `401`

前端影响：

- 每日定岗的详情页、编辑页现在不保证“知道 bizId 就能打开”
- 定岗新增和批量新增的选人控件不能继续放出全量用户
- 当用户切换分管部门后，某些旧定岗记录可能从当前账号视角不可见，这是符合新规则的

前端建议：

- `AUserId`、`BUserId`、`CUserId` 的选人控件统一限制在当前可管理用户内
- 从列表跳转详情时，如果详情返回 `401`，直接提示无权限并返回列表
- 批量新增前，前端先校验所选用户是否都来自当前可见列表

建议提示文案：

- `当前定岗记录不在你的分管范围内`
- `所选定岗人员超出你的分管范围`

### 4.4 升级记录

接口：

- `GET /api/level/levelupgrade`

当前规则：

- 不传 `UserId` 时，返回当前分管范围内用户的升级记录
- 传 `UserId` 时，这个用户必须在当前分管范围内，否则返回 `401`

前端影响：

- 升级记录页面的用户筛选项不能再使用全量员工列表
- 如果页面支持手动回填历史筛选条件，恢复筛选值时要校验该用户当前是否仍可见

前端建议：

- 页面初始化时，如果本地缓存的 `UserId` 已不在当前可选用户集合内，应自动清空筛选条件

### 4.5 经验明细

接口：

- `GET /api/experience`
- `GET /api/experience/{expId}`
- `POST /api/experience`
- `DELETE /api/experience/{expId}`

当前规则：

- 列表查询默认只看当前分管范围内用户的经验明细
- 如果前端传了 `UserId`，该用户必须在当前分管范围内，否则返回 `401`
- 单条详情、人工新增、删除时，也会校验目标用户是否在当前分管范围内，否则返回 `401`

前端影响：

- 经验明细页的用户筛选不能再使用全量用户
- 人工加减经验弹窗不能对非分管用户提交
- 通过历史链接打开某条经验明细详情时，可能因无权限被拒绝

前端建议：

- 经验新增弹窗的目标用户下拉只允许当前可管理用户
- 删除按钮仅对当前列表返回的数据展示
- 对详情和删除的 `401` 做单独处理

建议提示文案：

- `当前经验记录不在你的分管范围内`
- `你只能为自己分管范围内的用户新增经验`

## 5. 前端需要调整的点

### 5.1 用户选择器统一收口

以下页面如果存在用户下拉、远程搜索、弹窗选择器，建议统一切到“当前分管范围用户”数据源：

- 账号关联
- 账号转移
- 每日定岗
- 升级记录筛选
- 经验明细筛选
- 人工新增经验

如果前端仓库目前还没有统一数据源，至少要避免继续使用全量用户接口结果做筛选项。

### 5.2 处理 401 的页面交互

建议前端对这类业务接口增加统一处理：

- 列表查询返回 `401`：提示无权限并停留当前页
- 详情接口返回 `401`：提示无权限并返回列表页
- 保存/删除返回 `401`：提示当前数据不在分管范围内，并刷新列表

建议不要把这类错误当成普通网络错误或系统异常。

### 5.3 本地缓存筛选条件清理

如果页面会缓存筛选条件，比如：

- `userId`
- `bizId`
- 当前选中的推广账号

那么在页面初始化时，需要校验这些缓存值是否仍在当前可见范围内。

否则会出现：

- 页面一打开就查出 `401`
- 页面下拉里没有该用户，但请求参数里还带着旧 `userId`

## 6. 推荐联调顺序

1. 先联调账号关联页，确认用户筛选、删除、转移都不会越权
2. 再联调每日定岗页，确认列表、详情、编辑、批量新增都能正确处理 `401`
3. 再联调升级记录和经验明细页，确认用户筛选改为分管范围用户后接口稳定
4. 最后联调玩家换绑页，确认当前账号只能看到分管账号关联的换绑记录

## 7. 前端联调结论

这次前端更新的重点不是新增字段，而是把页面交互从“前端可随便传目标用户”改成“前端只能操作当前分管范围内的目标用户”。

前端只要完成以下 3 点，联调就会比较顺：

- 所有相关页面的用户选择器切到当前分管范围用户
- 对详情/保存/删除接口的 `401` 做明确提示
- 清理历史缓存的越权 `UserId` 或记录 ID
